# Porting an Amiga game to C

Goal: C source that builds for the Amiga and for SDL3 (desktop, browser) and behaves like the original bytes. The original is the authority at every step; never "fix" something because it looks wrong.

## Layout of a port

The framework repository (amiga-decomp) holds shared tools; each game is `projects/<id>/`, selected explicitly (`python -m amiga_decomp --project <id>`), with no default game and no dependence on another project's layout. Game addresses, names, routines, data, media, reports and game-specific emulator forks belong under the project.

```
projects/<id>/
  AGENTS.md  README.md  DECOMPILING.md  PLAN.md  project.json   notes and the method as applied to this game
  host/        ami9000 Lua scripts (machine description, boot, lockstep, oracle cases)
  scripts/     generators and test drivers for this game (symbols, struct, amiga.asm, build, rename, lockstep, sweep)
  local/       git-ignored: Kickstart, original disks, installs, saves
  captures/    git-ignored: recordings, inputs, RAM dumps (bounded windows, compressed)
  native/      the reconstruction: its own repository, a submodule of the project
```

The reconstruction goes under `native/` and is self-contained, so it can be split out and published on its own:

```
native/
  README.md  COPYING  .gitignore  .envrc  flake.nix  flake.lock  sdl3-emscripten.nix
  Makefile                      Amiga build (m68k-amigaos-gcc): intro and game programs; `make sdl`
  src/                          the game in C: game.c, menu.c, boot.c, file.c ..., the state struct and declarations in game.h,
                                game.symbols (the single source of the variables), data.c and game.ld (generated), the intro's data
  src/amiga/                    only what the Amiga build has: loader.asm (the only assembly), hardware, display, memory.c, and the code that drives a chip the port replaces as a whole (the drive: disk.c)
  src/sdl/                      the SDL3 port of the machine: host, display, irq, sound, files, guest.c / guest_load.c / guest_members.h,
                                gen_fixups.py, Makefile, Makefile.web, README.md
  web/                          the browser page (shell.html, assets)
  scripts/                      what the build needs at run time (e.g. serve_web.py)
```

Rules:
- One game module (`game.c`) with address comments while the structure is unclear, not one file per routine; asm only in the loader. Split it as the last step, when it is clear: plan the modules as address ranges from the trace analysis (function and instruction counts per range, `skill/docs/handoff.md`), name them by subsystem (`draw`, `objects`, `weapons`, `title`, `sound`, `shop`), never by letter or author, and give each its header with every routine declared once (a hand-written `extern` copied into several headers drifts). Code loaded over other code at the same addresses (levels, a shop) is a module per program with its own code table.
- The shipping port has no drive: it reads the game disk's files directly, and the game's check that its disk is in always passes (no INSERT DISK screen). The dev build keeps whatever timing the lockstep needs.
- The shipping port has no test or debugging options: its command line is the user's (`--disks`, `--scale`, the renderer). Headless runs, frame limits, picture hashes and dumps, scripted input, memory exports and status prints belong to the dev build (`dev/`, driven from Lua), which sets the one thing it needs from the machine (`host_set_headless`) before the machine starts. A test flag added to the port's `main.c` for a first check is moved to the dev build the day the dev build exists.
- Generated files (`game.h` between its BEGIN/END markers, `data.c`, `game.ld`, `amiga.asm`, fixups) are checked in so the native repository builds alone. The generators and the tests that compare the port with the original live in the project (`projects/<id>/scripts`, `host/`).
- Original disks, ROMs, recordings and binaries are never part of `native/`; the port asks for the disk images at run time (`--disks DIR`, the page's file picker).
- License the native repository as the user chooses (`COPYING` in `native/`).

## 1. Start from the original

- Original disks are never committed. Run the original in an emulator driven by scripts; it is the oracle.
- Reconstruct executed code only (coverage of scripted and human runs). A branch to code that never ran ends the C function with `/* goes on at $ADDR */`; fill it in when a later run reaches it.
- The executed code comes from an **exact trace**, not from hooks: the core's hooks report an address that is sometimes two bytes off while the machine free-runs (the prefetch), a hook on an extension word fires too, and `ami.hook` keeps one function per address (a coverage hook silently replaces your control hook). Free-run to the frame you care about, then `ami.step(fn)` (exact instruction addresses; about 30,000 steps a second) recording each address, its count, the frames it first and last ran and its observed successors (successors expose interrupt entries and indirect jumps). Do the inputs of the run from the step callback by frame number so the run is the same one.
- The low RAM is overlaid by programs (the intro, the game, a level's code): record the first frame of every instruction and take RAM dumps at several frames; decode each address from the dump of its phase. Find where a program image comes from on disk by searching the ADF for a block of the RAM dump.
- Python tooling runs through `uv` (`uv run script.py`, dependencies declared in the script's PEP 723 header or the project's `pyproject.toml`), never a global `pip install`. Read the original with capstone (`Cs(CS_ARCH_M68K, CS_MODE_M68K_000)`) on a RAM dump taken at the moment the code runs, with the coverage marking which instructions executed: disassemble, then write the C by hand from that listing. Code loaded by the game's own loader overwrites earlier code, so dump RAM after it is in place.
- Every function carries `/* orig $ADDR: what it does */`. Name by what the code does; a provisional name is `fn_` plus the address.

## 2. Variables are one struct

- Each variable at an absolute address is one line in a symbols file (`name 0xADDR type`). Generators turn that into the declarations, the single state struct, the linker script, the constant-data file and the Amiga assembly shim. Never edit generated regions by hand; regenerate.
- There is one struct, named as the game (`struct Xenon2` in `game.h`, the variable `xenon2`), and it is the game's whole memory: identical to the original's memory, byte for byte, in every build. There is no switch and no `#ifdef` in `game.h`: the SDL port defines the variable; the Amiga build links it at address 0 (`_xenon2 = 0` in the linker script), so both builds reach every variable through the struct. Members are used as `<game>.name` (the struct variable, named as the game); the generator does not write a `#define name (<game>.name)` per member, which would make every member name unusable for locals, parameters and fields. Every other struct is a member of it or the element type of one of its arrays (the object pool, the list heads, the weapon slots, the star records, the sound channels, the constant tables of records such as the debris kinds). `game.h` holds this struct (generated from the symbols files, between the markers) and includes what the game's code needs from the hardware header; there is no second state header. Type every region that is a record: a table of records is `tab NAME 0xADDR RecordType COUNT` (the generator writes its initializers, an address field as the original's address), not a byte array read with `rd16(table + 6 * i)`. Raw bytes stay for what is raw (pixels, buffers, text). Name the fields of the record types by what the code does with them; a field that every kind of object uses for its own purpose keeps its offset as its name (`v28`) and the kinds that give it a meaning name it in their own comment, not by renaming it for all.
- Members sit at the offsets of their original addresses; gaps are one macro, `PAD(n)`, a byte array named by its line (`pad_` plus `__LINE__`), so the generator needs no names for them. A compile-time `LAYOUT_ASSERT` checks the offsets.
- When several things share the same region, the region is a union of structs, one struct per thing: the words of an object that each kind uses for its own purpose (`o->launcher.step`, `o->gate.number`; the first member is the raw words, which is the layout the loader byte-swaps), the blob of each level loaded over the others (`level1_data` .. `level5_data`, from `blob` lines in the symbols files, each blob described by a small spec that a generator turns into the struct and the load-time conversion lists). Use a union only for things that are truly different, and sparingly: never to give one value two views (a long and its halves, a word and its bytes), and never to avoid choosing a type. Where one name per word is enough, use a plain field. A word that only one kind uses is named in that kind. No accessor macros.
- Code must not depend on absolute addresses or byte offsets: use struct members. Records that still carry always-present padding are converted field-wise when loaded.
- **The port has one byte order, the host's; swapping bytes is allowed only when data is loaded and when it is saved.** The game's code has no `rd16/rd32/wr16/wr32` (or any helper, macro or wrapper type such as a pair of raw bytes) that switches byte order at the point of use: a read through such a macro is an endianness switch on the fly, it hides which data is typed, and it makes every access depend on knowing the data's origin. Everything the C reads or writes is a native typed field or array: the map's cells `uint16_t`, a picture's header a record of `uint16_t` fields (`struct Pic { hot_x, hot_y, width, height }`) followed by its pixel words as `uint16_t`, a path script a record of `int16_t` fields (`struct PathCmd { op; union of the arguments }`), an animation script records with a `uint32_t` picture and a `uint16_t` delay, a screen an array of `uint16_t` words (`SCREEN_PLANE_WORDS` words a plane, `SCREEN_ROW_WORDS` a row; the byte strides are `SCREEN_PLANE_BYTES`, `SCREEN_ROW_BYTES`), the tile masks `uint16_t` rows, a text or a sample bytes. The loader swaps each of them once, from a table generated from the specs (the symbols files, the blob specs, the record types: a field's type says how wide it is), when the disk's files or an image of the original's memory enter, and the saver swaps them back once when the memory is exported (the lockstep compares the exported bytes, savestates, files). A region that has no spec is a region the code does not read as words; if the code reads words from it, it gets a spec (its records, its array of `uint16_t`), however many places there are: describing them is the work, not an `rd16` at each use. On the big-endian Amiga build the swaps are the identity, and the same C runs unchanged.
- Blitter and display work on the screens in the original's byte order only inside the machine layer (`sdl/`, `amiga/`), which reads the native words of the screen where it needs the planes; the game code never sees bytes of a screen.
- A blob spec (`blobs/levelN.blob`, `shop.blob`) describes everything the loader converts, so the code reads members: `record NAME SIZE` / `OFFSET name TYPE [COUNT]` / `end` (records are global across the files and nest), and the member types `u8 u16 s16 u32 cell ptr code ptr:Tag NAME`. `ptr:Tag` is a typed pointer (`struct Tag *`), `code` a pointer to a C function of the original's code, a record is converted field by field, a `u8` without a count runs to the next member. Type the tables the code walks (the event lists are arrays of `SpawnRec`, the formations arrays of `SpawnDef`, the shot-picture tables `ptr:ShotPic`, the path tables `ptr:PathCmd`), and a member the code reads as an element of an array that spans several members stays contiguous (the generator asserts each offset). A table whose entries point at variables of the fixed memory needs those variables as symbols (`var shot_pic_a 0xf68 uint8_t *`).
- A pointer in a constant table (`tab` of a record type) is written by the generator as `(void *)&xenon2.NAME` when a symbol begins at that address, so name the target (`tab anim_debris_0 0x2abc uint8_t 6`); only an address of the original's code stays a number. A pointer kept in a word that only one kind of object uses is a typed pointer in that kind (`Object *ptr`); the generated loader converts the record's own pointer members only, so a small hook in the loader converts the kind's pointer by the object's type on load and on export (`object_pointers_to_host/_to_guest`).
- Addresses inside scripts (the picture of an animation step, the routine of a call step, the address a jump goes to) are `uint32_t` fields of the step's record, converted by the loader to the host's pointer or C function like any other pointer member, so the code reads `step->gfx` and calls `step->code`, with no `GPTR`/`GFN` at the use. A pointer stored as two 16-bit words that the original also uses as two separate words (the drill's target over `energy`) is the one case that is composed inline.
- **Keep macros to a minimum: a macro is for a constant, or for a register write the port must intercept, nothing else.** A pointer written into a chip's address register (`custom->bltapt`, an audio `lc`) is cast where it is written, `custom->bltapt = (uintptr_t)(src);`, with no wrapper macro (an `ADDR(p)` that only hides the cast): the registers are 32-bit and so are the pointers of every target (the Amiga, the `-m32` host, wasm32), so `uintptr_t` converts without loss and without a second cast, and a build with wider pointers should fail to compile instead of truncating. Before adding a macro ask whether a typed constant, an inline function, a field or the plain expression says the same.
- **Write accessors out, name indices, name by what the game calls it.** `xenon2.player`, `xenon2.weapon_slots[i]`, `xenon2.obj_list[LIST_ENEMY]`, not `PLAYER`, `SLOT(i)` or `obj_list[2]`: an index with a name in an enum is written with the name, and an array of lists the loader and a state swap treat as one block stays an array. Constants with a meaning (`WEAPON_REAR_SHOT`) are fine as defines or enums. Name functions and constants after what the game calls the thing, found in its own data (the shop's item table named the weapons: `give_rear_shot`, `laser_update`), not after a type code (`weapon_44`); two things the game gives one name and nothing separates are numbered (`mine_1`, `mine_2`) and the comment says so.
- **Code goes in the module for what it does.** A routine that takes the input is the game's frame flow (`game.c`), the plumbing and hit routines of the object lists are `objects.c`, the status panel is drawing, the drive and the starfields are modules of their own. A function with two names and one body (`free_object`, `unlink_to_free`) is one function with one definition and one declaration; a routine used as a function pointer cannot be only `inline` (every file would get its own address). A script that moves functions between files matches prototypes only at column 0 and without `=`, or it takes lines of an inline function's body for declarations.
- **A module's types live in the module's own header, not in a `types_*.h`.** `sound.h` holds the sound structs, then `#include "game.h"`, then the prototypes; the generated `game.h` includes the module headers before it declares the memory struct, so the memory struct sees complete types, and a header that is included first still works because its types come before its include of `game.h`. Two rules keep that sound: a header's type section uses only `types.h` and forward declarations (`struct Object *`), and a header included from `game.h` has no inline function that uses the memory variable (a macro is fine). What a generator makes (the blobs' structs) goes into the header of the level or the shop between markers, the records every level shares into `level.h`.
- Overlays are a union of named structs (one per variant), so nothing needs a cast; nothing else is a union. Put data and tables into structs rather than helpers or macros, unless raw (pixels, buffers). Constant tables are data, not code that fills them.
- A long the original keeps as two words (high word first) is either one 32-bit field, if every use can treat it as one value, or two separate 16-bit fields; never an anonymous union of a long and its halves. The loader byte-swaps a record field by its type, so a 32-bit field is swapped as 32 bits and two words as two words; read and write the pieces by shifting inline (`((uint32_t)hi << 16) | lo`, `hi = (uint16_t)(v >> 16)`), with no join/split helpers: they hide the fixed-point arithmetic. Try hard to merge into a 32-bit field before settling for two words: shift the constants the source uses (a speed of `$40` per step on the high word becomes `$40 << 16`) so the code works on the whole value. Longs in plain memory (a random state of five longs) are `uint32_t` symbols, not word pairs.
- A 16.16 position kept as an integer word and a fraction word (`x`, `x_frac`) is an exception that is correct only where just some uses need the fraction and most read the integer word as a plain 16-bit value; revisit it with the rule above. The fraction is not cleared when a pool slot is reused and only some kinds set it: say so in the field comment, do not assume zero.
- Clear a struct with `memset(&x, 0, sizeof x)`; clear per member if the struct overlaps other state.

## 3. C only, 68000 semantics

- No inline assembly; the only assembly is the Amiga loader. The C runs from boot, as the original does.
- Keep original widths and signedness (16-bit word arithmetic; `blt/bgt` signed, `bcs/bhi` unsigned). Register arguments become parameters; results the caller uses become return values.
- Convert endianness only where data enters from disk or a memory image, never in game logic.
- Amiga-specific code lives in its own directory; the SDL port reimplements it.

### Hazards of running the C on a little-endian host

The same C builds for the big-endian 68000 and the little-endian host, and four things only go wrong on the host (the oracle on the Amiga build cannot see them; run the port headless with a scripted input and look at game variables, e.g. the positions of the enemies and the score):
- Data keeps the original's byte order only until the loader has swapped it and after the saver has swapped it back; no game code reads a buffer in the original's order (no `rd16/rd32/wr16/wr32`); typed members and arrays are in host order from the moment they are loaded.
- A long that overlays two words in another view of the same record (a 16.16 position used as a long by one routine and as two words by the others) is wrong on the host: declare it as the pair of words, high word first, and compose it in the one routine.
- An address of the original's code stored in memory (a handler, an animation op) is turned into the C function through one generated table, in the Amiga build too (never the identity: it would jump into the original's machine code); in the host build an address with no C is a logging stub.
- Loops that wait for an interrupt or the beam call `HOST_IDLE()`; the beam registers (`vposr`, `vhposr`) are given values that put the beam in the vertical blank; the disk HLE takes emulated frames (the game's retry loops count them).

### No addresses in the game code

Typed members and positions replace every address and offset, so the port holds no number that is a place in the original's memory:
- Words of pictures, masks, cells, screens and animation scripts are `uint16_t` members (a pointer to them is `const uint16_t *`); the loader swaps them, the game code never does. Bytes written into a word buffer (`put_screen_byte`) pick the half of the word by the byte's parity.
- A screen, the map or a scratch area is addressed by position: `SCREEN_POS(screen, row, col)`, `MAP_ROW/MAP_CELL`, and a struct laid over a buffer that the game reuses (a disk work area over a screen) is cast over it. A table index that the original kept as a byte offset in a local is an index (`angle >> 5`, not `(angle >> 3) & 0x1c` then `/ 4`); an offset the game stores in an object field stays, it is state.
- Addresses inside data are typed fields: an animation step is `{ const uint16_t *gfx; uint16_t delay; }`, a call `{ zero, code }`, a jump `{ script }`; the loader walks the scripts (start points: members named anim, targets of pointer members named anim) and makes the longs pointers, the saver puts the addresses back. Memory the original reads past its end is a member (`beyond_512k`).
- A pointer that shares its words with another field (a long whose second word is also an energy) is a pointer only if the other field is never written while it is live; a stale value in a freed slot then differs from the original's and the lockstep comparison must leave that slot out.
- Pointer arithmetic after a retype from bytes to words changes scale silently: audit every `+=`, `-=` and index of a retyped pointer.

## 4. Verify in layers

1. Oracle per function: hook the original at entry, call original and C on the same machine state, compare the result register and chip RAM. Every function gets a case. Routines that wait for the vertical blank cannot be called with interrupts masked: have the oracle make the waits return at once on both sides (generate the list from the C: the functions that contain `HOST_IDLE`), and put a watchdog on every call (restore the state and report HUNG after some frames, or the first hang silently blocks every later case; each hung call also leaks one of the emulator's eight call slots). The scenarios must really exercise the code: take the savestates where the thing runs (check hit counts of a few routines per 500 frames of a cold run) and press the fire button as the game expects.
2. Lockstep: run the original and a dev build of the port side by side and compare at the same point of the program (section 4a), memory and picture. Exclude timing counters. Apply keys by sync point so the run is deterministic.
3. Sweep: run a fixed set of saved states against a stored reference; list known non-equal states in the reference. Never rebuild while a sweep runs.
4. A/B of build variants (for example optimisation levels): they must produce identical frames and audio. Delete audio dump files first if the writer appends.
5. Cold start: run the dev build headless from the first screen with scripted keys and compare its dumps (the shipping port has no headless mode).

What the oracle cannot check: routines it cannot call (interrupt handlers, loops that wait for the beam, results only in the condition codes) and functions no scenario calls (`calls 0`). The first kind is checked inside its caller or by the lockstep, the second is written from the listing with extra care; both are named as unchecked in the report. One emulator at a time.

Do not skip ahead by poking variables; play the regular run so the state is one the original reaches. Start processes through a pidfd-based runner, not `pkill -f` / `pgrep -f`.

### 4a. Lockstep with a dev build and an interactive Lua shell

The shipping port stays free of tooling (the port's folder holds only the port); the dev build is a separate target in a folder beside it that compiles the same game C and machine sources plus the Lua host (`dev/src`, `dev/lua`), and vendored third-party code lives in a top-level `third_party/`.

- **The dev build hosts Lua and nothing else.** It embeds Lua (vendored in the repository's top-level `third_party/`, never in the port's folder) and gives the scripts the machine as a global `port`: step and run frames, run to or hook a function by the address it has in the original (with callbacks), stop inside it, memory in the original's byte order (whole image, `peek8/16/32`), the picture, the stick and keys, load memory, disks, and raw sockets (`listen`, `accept`, `readline`, `read`, `write`, `close`). It has no command protocol of its own: `--lua SCRIPT` runs a script and `--lua-args TEXT` is the script's global `args`.
- **Interactivity is Lua's.** The control socket is served by a Lua script (`dev/lua/shell.lua`, started with `--lua dev/lua/shell.lua --lua-args PATH`), not by the dev build, and it is a regular interactive Lua shell, no framing and no commands of its own: a client (`rlwrap nc -U PATH`, or `socat`) gets the `> ` prompt, `>> ` for unfinished statements, expression values printed, errors with a traceback, `print`/`io.write` going to the client; globals and functions defined stay for the next lines; the port moves only while a line runs and stands still between lines, so a stop can be inspected at leisure. Binary results go to files from Lua (`io.open`), not through the socket.
- **The emulator side is the same kind of shell.** `ami9000_host --control PATH` is a Lua shell inside the lockstep script, with both sides in reach (the original's memory, the port's through a peer); put the helpers that read, poke and compare both sides (`port_read`, `port_poke`, `mem_diff`, a pause at an address) in the lockstep script, as the Gods port does. The lockstep drives the port through that same shell: the emulator can only start a peer as a process with pipes, so the shell script also serves stdin/stdout (`--lua-args -`), and the lockstep script sends lines of Lua (`port.step()`, a `sync(addr)` function it defines, `ram_out()`), waits for the prompt (set to a line it can wait for) and reads binary results as `BIN LEN` plus bytes. There is no separate peer protocol and nothing in the port's C knows one. A stop at a function can arrive without the hook having counted an entry: wait for the count, not only for the stop.
- **Savestates first.** Both sides need save and load of a complete state, and lockstep is built on them: the emulator has them (`snapshot_save/load`), so the dev build gets `port.save_state(PATH)` / `port.load_state(PATH)` (memory in the original's byte order, plus everything the machine layer keeps: custom registers, copper list pointers, blitter and Paula registers, CIA and keyboard state, the disk position, the frame count, pending interrupts). Priority order: (1) start both sides from the same state (the original's savestate imported into the port) instead of replaying from the cold start; (2) lockstep from any state the original has, so a late scenario (a level being played, a boss) is reached by loading, not by a long run; (3) on a first difference save both sides, so the stop can be reloaded and bisected; (4) a stored set of states is the sweep's input (section 4, item 3). A port that can only load memory (`loadram`) starts well from a state at a point where the machine layer has no pending work (a frame flip); anything else the state holds that is not in memory is a source of false differences, so list it.
- **The game runs as a coroutine** that yields at each `HOST_IDLE`, so the controller steps the port one frame at a time; `-finstrument-functions` (never on the generated code table) gives hooks by the original's address through the same table that maps addresses to C functions.
- **Sync points are program points, not instants:** the original takes real cycles and the port none, so compare at an entry of a function the game passes once a frame (the frame-flip routine; hook the entries that jump to it, not a wait loop that jumps to itself). The port starts from the original's memory captured at the game's first instruction.
- **Baseline of junk:** at the first sync point record which members already differ (what the original's memory held before the game, pointer fields with stale bits) and report only changes after that. Leave out members that depend on interrupt timing (frame counters; with a slow original also the music player and the random generator), as an option.
- **Picture:** the original's frame one frame after the sync point (the flip takes effect at the next vertical blank) against the port's picture; find the window of the port's picture in the emulator's frame once, by the shift and columns-per-pixel at which the lit pixels coincide. A constant mismatch of the whole picture is an alignment problem, not a game difference: check with the frame before and after.
- **Tolerant mode** leaves out what the original's interrupts make timing-dependent: music, sound-effect requests, the hardware mirror, the random generator, the joystick bytes, the key state. A picture counts when it equals the original's frame next to the usual one (counted at the end). After a gap of emulated frames (a disk load: the original takes its real time, the port none) the lockstep resyncs: it copies the original's memory into the port and restarts the baseline (`resync=N`).
- **Interrupt timing is not a game difference.** The original takes its vertical-blank interrupts at arbitrary points of an iteration, the port only where it waits (`HOST_IDLE`), so whatever the main code hands to an interrupt (sound requests, music, the hardware mirror, frame counters, the random generator's callers) is consumed at different points: leave those members out (`tolerant`), and let the picture match the original's frame next to the usual one (the flip takes effect at a vertical blank): count how often so a systematic offset is visible.
- **Compare byte by byte against the baseline,** not member by member: a large live member (the object pool) always changes, only the bytes that already differed at the first point are junk. Two addresses of one function (the routine and its jump-table thunk) are the same value: normalise them in the comparison.
- **What a lockstep from a mid-game state finds first** is the import: a record read through two views (a pointer in one, words in the other; two bytes in one, a word in the other), a `void *` that holds code or data, an array typed as raw words that is really records with pointers. The importer converts by the declared type, so declare the type the code uses; a cold start never meets these (the records are empty).
- **Drop into the places a played course does not reach.** A lockstep only checks what its course touches: the boss fights, the later levels, the corners of a level stay unseen for as long as the course does not get there, and a long play to reach one is no way to test it automatically. Make states at those places: from a state of the level, poke the scroll position the game's own respawn uses and announce a death (the respawn clears the level's objects and puts the map and the player there), run some frames with the energy kept full, save (`host/scenario.lua`, a table of named places, `probe=1` lists what is on the screen). The lockstep starts from such a state like from any other (`auto=1 state=NAME`), and the port alone starts from the state's memory (a dump of it loaded into the port, then a policy that moves and fires; a crash is the failure). Every level and every boss gets a place, and the places are part of the checks.
- **To find where a difference starts**, hold both sides at the first difference and ask them (the emulator's `--control` shell with the lockstep's helpers, `gdb -p` on the peer): the memory, the raw host representation, the function that owns the field. Counting calls with the original's hooks is only a hint: a hook also fires at labels inside a routine.
- **The lockstep is played, and shows three views: the original, the port and the differences.** The emulator's window is the original; the port's picture is a panel beside it and the pixels that differ (in red over the dimmed picture, or black when none) a second panel, redrawn while paused (`ami.panel`, `ami.rgb_diff`'s image), as the Gods port does. You play it: the keys of the window drive both sides, and the first difference pauses both so the three views stay on screen and the run can be inspected. Give the port the stick at the same points the original takes it (at a sync point, not when the key goes down), and forward the keyboard's own keys to the port as the same raw codes; what the keyboard handler leaves in memory depends on when the key went down, so leave that state out (`key_table`, `key_code`) in play mode. Without the window (`--headless`) the same script runs unattended with a stick schedule.
- **Use the three-view lockstep as the default way to check a port by eye and to find divergences:** run the lockstep in the emulator's window (not `--headless`) from a savestate where the game is running, play it, and watch the original, the port and the differences side by side; the first difference pauses both, and that stop is where to investigate. Headless runs with a stick schedule are for regression (a long unattended run, a result to quote), not for looking. Run the window detached (`setsid nohup ... &`), or it dies with the command that started it, and say in the log when the three views are on screen so a missing panel is noticed.
- **"Run the lockstep" means this one, launched by the agent for the user to play:** the windowed run with the three views (original, port, differences) and `play=1`, never a headless run or a command pasted back, unless the user says headless. Start it detached with the display variables (`DISPLAY`, `WAYLAND_DISPLAY`) and `--control SOCK` under the agent's own job directory, so the agent can inspect a stop itself; check that the process stays up and that the log says the three views are on screen. Start from the savestate the user names or the project's standard one (a level running), not from the cold start.
- **A disk load is gated, not timed.** The original's load takes its real time (a shop load: 810 frames) and the port's loader would have to guess it. Instead the dev build's loader waits (`port.disk_gate(true)`, `disk_waiting`, `disk_release`) until the lockstep releases it; the lockstep hooks the original's loader entry, hooks its return address, keeps the memory at that return, and when the port is parked in its loader gives it that memory and releases it. Both sides then stand at the same program point, whatever the load's duration, and the comparison's baseline starts again.
- **A menu that reads the stick through an interrupt decode has an input latency the port does not share.** The original's slow frames let its swap return without waiting for a vertical blank, so its next stick check runs before the interrupt has decoded the new stick; the port's swap always waits for one, so it acts a frame earlier. Wrong cursor moves follow, then different random-generator draws, then a different starfield. Give the port the stick one sync point later at the sync points reached from that code (the return address of the original's sync function tells), not everywhere: the level reads the stick on a path that needs no lag. A random-generator difference is a symptom of such a drift, not a cause: find the first difference of anything else.
- **A frame of the port must contain a vertical blank.** The original's flip routine waits for a minimum of blanks since the last flip and then for the beam, so its frame always takes real time; if the counter it compares is already past the minimum (after a long stretch elsewhere), the port's wait loop falls through at once and the frame has no blank, so the interrupt that decodes the stick (and everything else it does) runs a frame late there. Idle once in that case.
- **The three views need the port's picture located in the original's frame.** Give it (the window, its scale and the frame offset are the same every run) rather than finding it from lit pixels, which fails when the screen is full; and start comparing pictures at the first sync point where the two agree: the port's colour and scroll registers come from its own run until the game rewrites them, so a state taken mid-fade differs for a few frames. Fail if they never agree.
- **One routine can have several addresses, and the code decides by value which it meets.** The base game stores the routine's address, the level's code (another part of the image) stores the jump-table entry that jumps to it, and the code that asks (`cmpi.l #$3130,6(a2)`) compares with one of them: an object that carries the other is not "the same" to it. A port that maps both addresses to one function loses that, and the difference shows only when the game reaches the compare. Give each address its own function when the code compares, store the one the original's code at that place stores (the functions that came from the level's image use the table entries), and scan the original's code for the immediates (`cmpi.l`/`move.l #addr`) to find the places.
- **A lockstep is only as good as the play it checks.** A long run in which the player is dead, stuck at an edge or waiting for a button press is two identical idle games: measure progress (the level's scroll position, the score, the energy) and say it with the result. A fixed stick schedule or a reactive autoplayer reaches little. Plot a course instead, with the port as its own simulator: from a state where the game is running, at each sync point save the port's state (`port.save_state`), try every stick option for a few intervals, score each (progress, score, energy lost, room to dodge), `load_state`, play the best for one interval; write the sticks as an input file that the lockstep replays (`replay=`) on both sides, in the window with the three views to watch it. It is fast (the port runs far faster than the emulator) and exact (the same input at the same sync points gives the same run). Beware: the game's own rules shape the course (here the level only scrolls on while the ship is held high on the screen, a death needs a fresh press of the fire button, a reversal of the stick passes through neutral); a planner that maximises safety parks where nothing happens, so reward progress and score, and check the course's own progress before using it.
- **Levels loaded over one another share addresses.** The level blob (code, tables, pictures) of each level is loaded at the same addresses, so the table of C functions by original address is per level (`level2 $ADDR` tags beside `orig $ADDR`, chosen while that blob is loaded) and each level's blob is a member of the union, with its own conversion list run when that level is loaded (the shop's blob is described by a spec like the levels', so its tables, records and pictures are typed members). Members of one level that other levels overlay are never converted by a general table: that would swap the bytes of the other level's tables. Code of the level that has no C yet must not crash the port: it resolves to a function that does nothing and is reported once, so a lockstep over a long play shows which function to write next. An ambiguous pointer (a field that holds a picture address in one object and a routine in another) must not be resolved to that stand-in.
- **Words that no member names are the original's bytes until a place reaches them.** The loader converts members only, so a picture, a tile, an animation script or a path script that lies outside every member is big-endian in the port: the blitter reads it as swapped words and a `struct Pic` read gives garbage, but only when a course draws it. Do not rely on the course to find the members: list the words that the specs' pointers reach (scripts from their start steps up to the step that ends them, the pictures the steps show, path scripts by their commands, the tile area up to the largest cell the map and the cell tables use) from a dump of the original's memory and make them members (a tool, regenerated when a spec changes); a script that is reached through a member that is not named as a script (a table of cells that is also a script) is converted only if it is named so. A walker that follows a script past its end step converts the data that follows it.
- **Poison the unnamed memory and compare.** Instead of hunting untyped words by eye: from a dump of the original at a place, make a copy in which every byte that no member of the port names (the gaps of the memory struct, the paddings of the level blob; not data the code legitimately takes as bytes, like the sample bank) is 0xA5, load each into the port and play the same inputs; the picture hashes and variables of the two runs must be equal. A difference is a read of memory that has no name (an untyped picture, script or table, or an address computed past a member); bisect it by poisoning halves of the address range. This finds in minutes what a played course finds never, and it applies to every place the drop-in scenarios make.
- **A raw read of memory that has a named member reads the host order.** Reading a variable by its address (`*(uint16_t *)GPTR(0x3f03c)`) when a member covers it gives the byte-swapped value on the host and the right one on the Amiga: use the member. The lockstep found it as an object stepping when the original's did not.
- **A savestate taken where the original waits for a button press cannot be imported into the port** (the port's own flow is somewhere else: it scrolls on). Make a state a few frames after the press (`host/state_after.lua`) and start the lockstep from that.
- **Frame cadence:** a port stopped inside a hooked function is mid-frame; do not run its frame-end work again on resume, or the port takes extra frames per sync point.
- **The input a routine saw is the one at its read, not at its entry.** The original's interrupt decodes the stick in the middle of a slow frame, so a routine that reads it after a long call (an option's animation step) can see a newer byte than at its entry. Record the byte at the read instruction of each reader (keep the entry's record so a call that returns before reading stays aligned) and give the port that value at the entry. Live stops that a recorded replay never repeats are this class; step the port only after the input is in (`live=0`).
- **A pointer kept in two words of an object must be the guest address,** not the host pointer (the drill's target in its `$30/$32`): the port works with its own, and the lockstep, an imported state or a memory replaced by the original's finds it. Use the guest-address helpers both ways.
- **Which end of a list an object goes in is told by the pointer the original uses** (the head cell or the tail cell of the sentinel): a transcription that appends where the original inserts at the head shows only as a different order of the list, one object late. Check every insertion against the disassembly.
- **Recursive descent over a memory dump finds a level's code** from its entry table: follow the stored `#ADDR`/`lea` operands and the record tables whose fields are update, draw and hit pointers; add the loop branches (`dbge`, `dbhi`, ...) to the list of branches; tables and strings decode as garbage code, ignore it. A code table generated from a template needs a look at the generated file (a digit replaced everywhere changed an address range and the lookup missed).
- **A routine that leaves registers for the next one** (a test of the point `d0/d1` that the caller left, a call with an address register that is overwritten right after) must be written with the values the original had, not the ones the name suggests.


## 5. The SDL port reimplements only the machine

Display, copper, blitter, interrupts, sound mixer, disk access and the memory image are the port's. Game files load member by member through a member table, with generated fixups for structs inside disk records. The Amiga build has no libc: supply `memset`/`memcpy` yourself (and keep the compiler from turning their loops into calls to themselves).

High-level emulation, not chip emulation: no beam, no DMA slots, no chip timing. The C that drives a chip stays faithful (it runs on the Amiga and in the oracle) and lives in `src/amiga/` (the drawing that sets up the blitter, the drive); the port does not emulate the chip: `src/sdl/` implements the same functions on what they act on (a bob is drawn pixel by pixel into the planes, clipped to the screen; a tile, the background, the text and a sector read are copies), and a sound player writes voices (`audio_data`, `audio_length`, `audio_period`, `audio_volume`, `audio_start`, `audio_stop`: `amiga/audio.c` writes the channel registers and DMA bits, `sdl/sound.c` mixes them) instead of the chip's registers; the set/clear registers that are left go through `SETCLR_WRITE` (`intena`, `intreq`). A refactor of this kind is checked by hashing the mixed samples of the same plays in the build before and after (identical hashes), not by ear. The result is checked by the lockstep: the same bytes in the screens, and the margin a blit writes outside the screen (named, and left out of the comparison) is the only difference. Keep a removed emulation as a git tag if it may be wanted later. A routine that is better replaced as a whole (the game's disk loader, a chip delay loop) lives in `src/amiga/`, which only the Amiga build compiles, and the port defines in `src/sdl/` just the functions the game's other code calls (`disk_read_sectors`, the disk interrupt): no weak symbols, no `HLE_WEAK`, and the low-level helpers (motor, head steps, MFM) are static in the Amiga file because nothing else calls them. The picture is made once a frame from the registers the CPU set and the copper list the game leaves in memory, read as data (MOVE and WAIT per scanline). Sound is a mixer fed from the channel registers (lc, len, per, vol, DMACON). Waits for an interrupt are written `while (!flag) HOST_IDLE();`: the host runs the due interrupts there, one video frame of emulated time per call. Where the picture cannot be derived this way, the oracle layers (section 4) compare frames. Gods (`src/sdl/display.c`) and Xenon 2 (`src/sdl/display.c`, `blitter.c`, `sound.c`, `disk.c`) are references.

## 6. Browser build

Emscripten (wasm32, pthreads). The program runs on a worker thread; `emscripten_set_main_loop` does vblank, drawing and sound; disk images go to the in-memory file system from the page; persistent data uses IDBFS; a phase switch joins the worker and starts the next phase. Turn the renderer's vsync on, or SDL runs the main loop on a timer. Serve with a script that sets the cross-origin-isolation headers threads need.

## 7. Working rules

- Build inside the reproducible shell: `flake.nix`, `flake.lock`, `sdl3-emscripten.nix` and `.envrc` (direnv `use flake`, with the retrofoundry cachix cache) in this folder are the reference; copy them into the port's repository and adjust the names (the flake's `GAME_*`/`game.*` names must match the port's Makefiles). It provides the m68k-amigaos-gcc toolchain, SDL3, Emscripten and `nix build .#web`. Run builds with `nix develop --command ...`.
- **Check a refactor against the build before it.** Make a `git worktree` of the commit before the move, build both, and run the same plays (the menu, the shop, several levels from `exercise.lua`, the idle lockstep) on each: identical picture hashes mean only code moved. A difference that the same run shows on both sides (a lockstep that stops after a few syncs) is not yours.
- Small commits, each with a summary; pushes carry `[skip ci]` where the project asks for it; push only when asked.
- Name every local and parameter for what it holds (`obj`, `shot`, `x`, `angle`, `count`), not for the register it was in (`a0`, `d0`); parameter names in a prototype equal those of the definition. Where one register held two things, give each its own declaration of the same type, with no change of casts, widths or statement order; list the functions you split in the commit message, because a lockstep proves them only on the paths it reaches.
- A naming pass over many files can be run in parallel by file: each agent edits only its own files, runs no build, and checks them with `gcc -fsyntax-only`; one full build and the lockstep follow. Do not let agents share a scratch script path: two overwrote each other's.
- Framework tools and per-game analysis stay in the framework repository; the port's repository holds the reconstruction and the generated files its build needs.
- A generated list is rebuilt only when its inputs changed, so a generator that fails once looks fixed on the second `make`: read the first error. The record parser reads the struct headers, so a typedef'd struct (`typedef struct Cell { ... } Cell;`) must be one it accepts; run the generators from scratch (`touch` them) when a header changes.
- A type change that the compiler accepts silently (a `uint16_t *` given a byte offset `p + 0x28` adds twice the distance): after retyping a pointer, grep for the offsets that used it, and run the lockstep from the start of the game as well as from the levels, since the title and the menus run only from the start.

## 8. The oracle: ami9000 (this repository)

Multi-disk games and runtime checks: `content` can be an `.m3u` (the first image in DF0); `ami.disk_count/index/eject/select` swap floppies (eject, wait ~20 frames, select, insert; a savestate restores disk 1 again, so scripts that load a disk-2 level start from a cold boot or swap after the load). A host script ends with `ami.quit()`, or the process runs until its timeout.

This repository, `git@github.com:borancar/amiga_porting.git`, carries the emulator host every check above runs on. Clone with `--recurse-submodules` (`ami9000/engine9000-src` is the pinned Engine9000/PUAE source). Binaries are never committed; build them:

```
ami9000/host/build_core.sh     # patched PUAE core -> ami9000/build/system/ami9000.so (patches listed in ami9000/patches/series)
make -C ami9000/host           # host -> ami9000/build/ami9000_host   (needs SDL3 and Lua 5.4)
ami9000/build/ami9000_host game.lua [--headless] [the script's own flags]
```

- A game is one Lua script: `ami.machine{ model, content (adf, .slave or "@blank"), files, roms = {{"kickNNN.rom", crc32}}, opt = {...} }` then `ami.boot()`. Kickstarts and disks are never shipped; keep them in the project's ignored `local/` folder.
- After `ami.boot()` the script is a coroutine resumed once per core frame: `ami.wait(n)`, `wait_until(fn, max)`, `peek/poke 8/16/32`, `read/write`, `reg/set_reg`, `key`, `pixel/frame_hash/screenshot`, `snapshot_save/load`, `pause/resume`. Hooks run a Lua body when the CPU reaches an address (this is how the per-function oracle calls the original and the C on one state). `ami.import("amiga/lockstep")` is the frame-locked lockstep driver against a native peer (the peer speaks `key`/`step`/`image`/`quit` over stdin/stdout); `amiga/hunk`, `amiga/exec`, `amiga/dos13` load hunk executables and take over Kickstart 1.3 boot.
- `--control PATH` serves a socket; `ami9000/host/ctl.py PATH 'ami.reg("pc")'` runs Lua lines in the live script, including while it is paused. Use it to inspect a stop.
- Run it under `ami9000/pidrun.py [--timeout S] -- COMMAND` so it can be waited on, timed out and killed through a pidfd.
- Transcribing hazards (results in the flags, code after a call, interrupt handlers, self-modifying code, stale addresses): `skill/docs/transcribing.md`. The files a project keeps (PLAN, HANDOFF, DECOMPILING) and the work packages: `skill/docs/handoff.md`.
- Full API, flags and the core patches: `ami9000/host/README.md`; how a Lua loader takes over a WHDLoad-style game: `ami9000/WHDLOAD.md`. Each port keeps its own scripts under its project (e.g. `projects/<id>/host/*.lua`), not here.
- Patches that do not apply to the pinned source (checkpoint, clock, transfer, live-display, pc-observer) are kept in `ami9000/patches/` but are not in `series`.
